# Требования к внешним интеграциям сервисов "Умный дом"

Требования к интеграции PropDevelopment с партнёрской платформой "Умный дом"
(интеллектуальный домофон и интеллектуальный шлагбаум).

Категории: **О** - обязательное до запуска, **Р** - рекомендуемое.

## 1. Требования к безопасности

### 1.1. Разграничение ролей операторов персональных данных

| № | Требование | Кат. |
|---|---|---|
| 1.1.1 | Роли сторон зафиксированы в договоре: PropDevelopment - оператор ПДн, партнёр - обработчик по поручению оператора. Обработка биометрии выполняется на стороне партнёра | О |
| 1.1.2 | Биометрические шаблоны и видеопоток не передаются в системы PropDevelopment и не хранятся в них. В smart-home-db хранится только идентификатор шаблона на стороне партнёра и признак наличия согласия | О |
| 1.1.3 | Согласие собственника на обработку биометрии оформляется отдельно от согласия на обработку прочих ПДн, с возможностью отзыва без потери доступа к остальным услугам | О |
| 1.1.4 | При отзыве согласия PropDevelopment вызывает удаление биометрического шаблона у партнёра и фиксирует подтверждение удаления в журнале | О |
| 1.1.5 | Договор с партнёром содержит требования по защите данных, порядок уведомления об инцидентах в срок не более 24 часов и право PropDevelopment на аудит | О |
| 1.1.6 | Подтверждено размещение серверов партнёра, обрабатывающих ПДн граждан РФ, на территории РФ | О |

### 1.2. Ограничение состава передаваемых данных

| № | Требование | Кат. |
|---|---|---|
| 1.2.1 | Состав полей каждого метода API зафиксирован в контракте. Передача полей, не перечисленных в контракте, отклоняется шлюзом | О |
| 1.2.2 | Партнёру передаётся минимально достаточный набор: идентификатор объекта доступа, псевдонимизированный идентификатор жильца, срок действия доступа. Ф. И. О., телефон, e-mail, лицевой счёт и данные о задолженности не передаются | О |
| 1.2.3 | Связь псевдонима с реальным собственником хранится только в smart-home-db на стороне PropDevelopment | О |
| 1.2.4 | Номера транспортных средств передаются в виде хеша с солью; сверка выполняется по хешу | Р |
| 1.2.5 | Ответы партнёра фильтруются шлюзом: поля, не предусмотренные контрактом, не попадают в системы PropDevelopment | О |
| 1.2.6 | В аналитическое хранилище передаются только обезличенные события доступа без идентификаторов жильцов и номеров ТС | О |

### 1.3. Изоляция арендаторов и проверка прав на объект

| № | Требование | Кат. |
|---|---|---|
| 1.3.1 | Каждый запрос к партнёрскому API сопровождается идентификаторами ЖК и управляющей компании; шлюз проверяет, что объект принадлежит арендатору, от имени которого выполняется запрос | О |
| 1.3.2 | Проверка принадлежности объекта выполняется на стороне сервера и не зависит от параметров, передаваемых клиентским приложением | О |
| 1.3.3 | Токен доступа партнёра ограничен перечнем ЖК, обслуживаемых этой управляющей компанией | О |
| 1.3.4 | Собственник может управлять доступом только к тем объектам, где подтверждено его право собственности или проживания | О |
| 1.3.5 | Реализованы негативные тесты изоляции: запрос данных чужого ЖК и чужого лицевого счёта завершается отказом. Тесты включены в регрессионный набор | О |

### 1.4. Защита канала и данных

| № | Требование | Кат. |
|---|---|---|
| 1.4.1 | Весь обмен - по TLS 1.2 или TLS 1.3. Обычный HTTP запрещён | О |
| 1.4.2 | Взаимная аутентификация сторон по mTLS с закреплением сертификата партнёра | О |
| 1.4.3 | Данные шифруются при хранении: smart-home-db - на уровне БД, резервные копии - на уровне хранилища. Алгоритм AES-256 | О |
| 1.4.4 | Ключи и токены интеграций хранятся в secret-manager (HashiCorp Vault), в коде и конфигурационных файлах не размещаются | О |
| 1.4.5 | Ротация ключей и токенов партнёра - не реже одного раза в квартал, автоматически, по стратегии переключения с сохранением предыдущей версии до завершения перехода | О |
| 1.4.6 | Операции с ключами журналируются: кто, когда и для какой интеграции получил доступ | О |
| 1.4.7 | Токены доступа не передаются в параметрах URL | О |

### 1.5. Целостность команд и событий

| № | Требование | Кат. |
|---|---|---|
| 1.5.1 | Команды открытия домофона и шлагбаума подписываются и содержат идентификатор запроса, метку времени и срок действия не более 30 секунд | О |
| 1.5.2 | Реализована защита от повтора запроса (replay): повторный идентификатор запроса отклоняется | О |
| 1.5.3 | Входящие webhook-события партнёра проверяются по подписи; события с неверной подписью отклоняются и фиксируются как инцидент | О |
| 1.5.4 | Команды идемпотентны: повторная отправка с тем же идентификатором не приводит к повторному открытию | О |
| 1.5.5 | При недоступности партнёра применяется отказ в открытии по умолчанию (fail-closed) для биометрического доступа; открытие по звонку собственника остаётся доступным | О |

### 1.6. Доступность и устойчивость

| № | Требование | Кат. |
|---|---|---|
| 1.6.1 | На стороне шлюза установлены квоты и ограничение частоты запросов на партнёра и на объект | О |
| 1.6.2 | Настроены таймауты и размыкатель цепи (circuit breaker) при вызовах партнёра, чтобы отказ партнёра не влиял на услуги ЖКУ | О |
| 1.6.3 | Уровень доступности сервиса партнёра и время реакции на инциденты зафиксированы в SLA | О |
| 1.6.4 | Локальный сценарий открытия по звонку работает при недоступности интеграции | Р |

### 1.7. Аудит и мониторинг

| № | Требование | Кат. |
|---|---|---|
| 1.7.1 | Журналируются: вызовы партнёрского API, изменения списков доступа, выдача и отзыв согласий, события проходов и проездов, отказы в доступе | О |
| 1.7.2 | Запись журнала содержит: время, идентификатор запроса, инициатора, партнёра, объект, результат. ПДн, токены и номера ТС в журналы не записываются | О |
| 1.7.3 | Журналы передаются в подсистему аудита (SIEM), настроены оповещения на аномалии: серия отказов в доступе, массовое изменение списков, вызовы вне рабочего окна | О |
| 1.7.4 | Журналы событий доступа хранятся не менее одного года, доступ к ним ограничен и сам факт доступа журналируется | О |
| 1.7.5 | Собственник видит в мобильном приложении историю проходов по своему объекту | Р |

## 2. Протоколы аутентификации и авторизации

### 2.1. Выбор протоколов

| Участник обмена | Аутентификация | Авторизация | Обоснование |
|---|---|---|---|
| Собственник -> мобильное приложение | OpenID Connect (надстройка над OAuth 2.0), auth-service-1 [Keycloak]. MFA при привязке нового устройства и при изменении списков доступа | Проверка прав на объект в smart-home-app | OIDC уже поддерживается Keycloak; передаёт идентификационный токен между сервисами без передачи пароля |
| Мобильное приложение -> smart-home-app | Access token OAuth 2.0 (JWT), проверка подписи и срока действия | Области доступа (scopes): `smarthome.read`, `smarthome.open`, `smarthome.acl.write` | Разделение чтения, открытия и управления списками ограничивает последствия перехвата токена |
| smart-home-app -> smart-home-gateway -> partner-api-gateway | Внутренняя аутентификация сервисов по mTLS | Роль сервиса | Служебный обмен внутри контура компании |
| PropDevelopment -> партнёрская платформа | OAuth 2.0, поток Client Credentials, плюс mTLS | Области доступа, ограниченные перечнем ЖК: `device.command`, `acl.sync`, `biometry.enroll` | Client Credentials предназначен для обмена между системами без участия пользователя; mTLS исключает использование украденного токена с чужого узла |
| Партнёр -> partner-api-gateway (webhook) | Подпись тела запроса HMAC-SHA256 либо mTLS-клиентский сертификат | Приём только событий по объектам, закреплённым за партнёром | Подпись подтверждает подлинность и целостность события |
| Оператор УК -> smart-home-app | OIDC через партнёрский раздел auth-service-1 либо федерация SAML с системой УК | RBAC роль `uk-operator` плюс атрибут принадлежности к УК (ABAC) | SAML применяется, если у УК есть собственный поставщик идентификации и требуется SSO между доменами |
| Сотрудники PropDevelopment | Active Directory, Kerberos внутри домена | RBAC согласно ролевой модели | Существующая служба каталогов компании |

### 2.2. Требования к токенам и сессиям

| № | Требование | Кат. |
|---|---|---|
| 2.2.1 | Срок жизни access token - не более 15 минут, refresh token - не более 30 дней с привязкой к устройству | О |
| 2.2.2 | Токен содержит идентификатор субъекта, области доступа, перечень доступных объектов и срок действия. Права не расширяются на основании данных, переданных клиентом | О |
| 2.2.3 | Токены партнёров выдаются отдельно на каждую управляющую компанию; один токен на всех партнёров не используется | О |
| 2.2.4 | Реализован отзыв токенов: при отзыве согласия, смене устройства, расторжении договора с партнёром | О |
| 2.2.5 | Для действий с повышенным риском (изменение списка доступа, регистрация биометрии) требуется повторное подтверждение личности | О |
| 2.2.6 | Административный доступ к настройкам интеграции выдаётся по модели Just-In-Time на срок не более 24 часов с журналированием действий | Р |

### 2.3. Модель авторизации

| № | Требование | Кат. |
|---|---|---|
| 2.3.1 | Базовая модель - RBAC. Роли: собственник, член домохозяйства, оператор УК, инженер поддержки, администратор интеграции | О |
| 2.3.2 | RBAC дополняется атрибутами (ABAC): принадлежность к ЖК, принадлежность к УК, статус права собственности, действующее согласие на биометрию | О |
| 2.3.3 | Решение об авторизации принимается в одной точке - smart-home-app; шлюз повторно проверяет границы арендатора перед вызовом партнёра | О |
| 2.3.4 | Действует принцип минимальных привилегий: по умолчанию доступа нет, права выдаются явно | О |
| 2.3.5 | Права на объект пересматриваются при изменении статуса собственника; при прекращении права собственности доступ отзывается автоматически | О |

## 3. Организация взаимодействия систем

### 3.1. Схема взаимодействия

```
Собственник -> Витрина сервисов для собственников (mobile)
                      | OIDC, REST
                      v
              smart-home-app --> smart-home-db (списки доступа, согласия, журнал)
                      |  ^
        REST          |  | Kafka (события)
                      v  |
              smart-home-gateway --> secret-manager (ключи)
                      | REST
                      v
              partner-api-gateway <---- webhook с подписью ---- Партнёрская платформа
                      | OAuth 2.0 + mTLS                              "Умный дом"
                      \--------------> Партнёрская платформа  --> оборудование дома
                      |
                      |--> Системы управляющих компаний (REST, OAuth 2.0)
                      \--> SIEM (журналы вызовов)
```

### 3.2. Принципы взаимодействия

| № | Требование | Кат. |
|---|---|---|
| 3.2.1 | Все обращения к внешним системам идут через partner-api-gateway. Прямые вызовы партнёрских API из продуктовых сервисов запрещены | О |
| 3.2.2 | Существующие интеграции с API управляющих компаний переводятся на шлюз, чтобы к ним применялись единые политики | О |
| 3.2.3 | smart-home-gateway - единственный компонент, знающий особенности протокола партнёра. Смена партнёра не затрагивает smart-home-app | О |
| 3.2.4 | Синхронные вызовы применяются только для команд, требующих немедленного ответа (открытие домофона и шлагбаума) | О |
| 3.2.5 | События доступа передаются асинхронно через smart-home-events [Kafka], чтобы пик событий не влиял на доступность услуг ЖКУ | О |
| 3.2.6 | Списки доступа синхронизируются с партнёром по расписанию и по событию изменения, с фиксацией версии списка на обеих сторонах | О |
| 3.2.7 | Расхождения списков выявляются регулярной сверкой; при расхождении приоритет имеет версия PropDevelopment | О |
| 3.2.8 | Мобильное приложение обращается только к внутренним сервисам PropDevelopment и не вызывает API партнёра напрямую | О |

### 3.3. Контракт и версионирование

| № | Требование | Кат. |
|---|---|---|
| 3.3.1 | Контракт API согласован в машиночитаемом виде (OpenAPI) и включает состав полей, коды ошибок, лимиты | О |
| 3.3.2 | Контракт версионируется; изменение состава передаваемых данных требует согласования со специалистом по ИБ | О |
| 3.3.3 | Изменение контракта проходит проверку на состав ПДн до вывода в промышленную эксплуатацию | О |
| 3.3.4 | Ведётся реестр интеграций: партнёр, назначение, состав данных, владелец, срок действия ключей | О |

### 3.4. Тестирование и приёмка

| № | Требование | Кат. |
|---|---|---|
| 3.4.1 | Интеграция тестируется на обезличенных данных; использование реальных ПДн в тестовых средах запрещено | О |
| 3.4.2 | До запуска проводится проверка изоляции арендаторов и сценариев отказа партнёра | О |
| 3.4.3 | Партнёр допускается к промышленной эксплуатации после оценки рисков и согласования специалистом по ИБ | О |
| 3.4.4 | Определён порядок вывода интеграции из эксплуатации: отзыв токенов, удаление данных у партнёра, подтверждение удаления | О |
